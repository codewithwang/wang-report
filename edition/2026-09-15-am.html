GitLab And Gitea Bugs Put Repos Under Siege

A perfect-score GitLab flaw and active Gitea exploitation across six countries mean the code repository, not the perimeter firewall, is this week's real attack surface.

The number to sit with is ten, as in a perfect 10.0 CVSS score, and it belongs to CVE-2026-85706, a path traversal flaw in GitLab Community and Enterprise Edition. Path traversal means an unauthenticated request can walk out of the web root and read whatever the GitLab process can see: source code, CI/CD secrets, SSH keys, deployment tokens sitting in commit history nobody scrubbed. CISA issued its own alert. HKCERT's bulletin the same week bundles it with separate GitLab flaws enabling remote code execution and cross-site scripting, so an exposed instance this week faces all three at once.

What showed up alongside it is why this is a story and not a routine patch note. The Hacker News reported a suspected Chinese group tracked as Red Heron already exploiting a Gitea remote code execution bug live, thirteen organizations breached across six countries. Different product, different vendor, same category of target: internet-facing code repository infrastructure that most security teams still file under internal tooling rather than perimeter defense. Kai Tanner's Cyber Intel desk has the full audit trail: GitLab is disclosed with no confirmed exploitation yet, Red Heron's Gitea campaign is already running.

A self-hosted GitLab instance is not an internal dev tool this week. It's a server holding the keys to production, and Red Heron has already shown what happens to the version of this bug that gets exploited before anyone patches. Patch on the assumption that the disclosure and the exploitation report arrive in the wrong order, because for Gitea's thirteen victims, they already did.
